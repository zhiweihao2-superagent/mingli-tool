# AI 解读输出协议 v1

`mingli-ai-interpretation/v1` 是模型输出与前端之间的稳定边界。输入必须是已经通过校验的 `mingli-ai-input/v1`，输出还要再次经过本地验证，不能直接展示模型原文。

## 输出结构

- `mode`：`mock` 表示模拟网关，`model` 表示旧版简报，`model-report` 表示分批生成后合并的完整报告。
- `contractId`：由输入事实包指纹组合而成，便于核对输出对应哪一张盘。
- `summary`：普通话总览，必须带事实路径和置信等级。
- `sections`：普通模式为 1 至 8 个主题；完整报告固定为八字 7 主题与紫微 13 主题，共 20 个主题，并按报告计划顺序返回。
- 完整报告主题额外包含 `oneLineSummary`、`evidenceExplanation` 与 1 至 3 条 `practicalAdvice`。
- `limitations`：必须明确说明局限。
- `audit`：输出验证结果和证据引用数量。

机器可读约束位于 `schemas/ai-interpretation-v1.schema.json`。浏览器运行时还会执行以下语义检查：

1. 每条 `evidencePaths` 必须能在本次事实契约中解析。
2. 每个主题必须标记为 `interpretation`，不能冒充排盘事实。
3. 禁止决定性、恐吓性、诊断性和投资指令措辞。
4. 不允许模型供应商返回未声明的主题。
5. 缺少局限说明、证据或反思问题时整体拒绝展示。

## 二十主题分批生成

浏览器将八字 7 个主题和紫微 13 个主题按每批最多 2 个发送到本机 `/api/v1/interpret`。服务端不会把整份事实契约原样转交模型，而是从 `mingli-report-plan/v2` 中抽取本批主题允许使用的证据路径与对应值。每批必须：

1. 只返回请求的主题，并保持请求顺序；
2. 所有引用路径可在原始事实契约中解析；
3. 通过文字安全、字段完整性和证据校验；
4. 截断或结构失败时先采用紧凑格式重试；双主题仍失败时，浏览器拆成两个单主题请求；
5. 20 个主题全部成功后才合并展示，避免以残缺报告冒充完成。

八字 7 个主题依次覆盖四柱与日主、扶抑旺衰、月令格局与特殊格候选、扶抑/格局/调候三轴喜用、寒暖燥湿调候、原局合冲刑害、大运流年坐标。模型只能解释 `bazi-derived-rules/v2` 已计算的候选、证据和反证，不能自行重排或把候选改成唯一结论。

紫微格局候选仅在“命格总览”批次提供，并只包含排盘规则已经命中的 `matched-candidate`；模型必须同时看到成立条件、加分项和破格项。八字主题只能引用八字路径，紫微主题只能引用紫微路径，服务端会在模型返回后再次校验这一边界。

## 模拟网关

`web/ai-interpretation.js` 暴露与未来真实网关一致的异步接口：

```js
MingliAiInterpretation.request(contract, { provider: "mock" })
```

本地版本通过持有服务端密钥的 `/api/v1/interpret` 调用 DeepSeek；密钥不会进入浏览器事实契约。没有本地授权勾选或 `.env` 未配置时，不发送模型请求。
