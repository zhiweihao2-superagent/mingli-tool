# 架构

当前数据流：

```text
JSON 请求
  -> 协议与字段校验
  -> 日期 时间 性别及规则标准化
  -> 固定提交的确定性八字引擎
  -> 统一结构化结果
  -> JSON 响应
```

`src/mingli_tool/bazi.py` 是适配边界，负责拒绝引擎不能真实支持的请求、调用上游函数以及把内部元组转换为稳定 JSON。`scripts/pai_pan.py` 保留上游算法，暂不在适配层复制历法公式。

CLI 只是薄入口，不保存出生资料。未来的 HTTP API 应复用同一个 `calculate()` 函数，不另写一套排盘逻辑。AI 解读也必须读取冻结后的 `calculation`，不得改变四柱、大运或来源信息。

紫微斗数网页原型采用独立链路：

```text
同一出生资料
  -> 时辰精度与子时边界检查
  -> 固定版本 iztro 2.6.2
  -> web/ziwei-adapter.js 稳定十二宫结构
  -> web/ziwei-facts.js 校正、关系计算与硬性校验
  -> 带版本和指纹的 AI 事实包 v4
  -> 紫微基础信息与十二宫展示
```

页面组件不直接读取 iztro 原始对象。v4 事实包先执行上游默认金标准修正（《斗数全书》亮度、辛年魁钺、截空副截、旬空副旬、年支大耗），再冻结节气与农历口径双四柱、生年四化、十二宫对宫与三合关系、空宫借星、小限、童限、长生/博士/将前/岁前、十二宫宫干飞出的四十八条落点、十二条本命化忌链、自化方向、完整大限，以及指定时间对应的大限/流年/月/日/时叠宫、四化、流曜和运限飞化。只有本命、飞化、运限与月日时各层硬性校验通过时，才允许后续 AI 读取对应层级。

自化使用固定的“同宫离心 ↓、对宫向心 ↑”位置规则生成带证据编号的事实；大限和流年各有十二宫飞化四十八条落点；流月、流日、流时各自提供五层叠宫、四化和流曜。真太阳时由统一时间层先完成校正，再把同一个公历时刻交给八字和紫微；解释性规则结论仍在 `unsupportedScopes` 中。未知时辰不会生成紫微命盘；仅知道“子时”也不会擅自决定是当天凌晨还是晚上 23 点。

八字由 `src/mingli_tool/bazi_facts.py` 生成 v1 事实包。这里把干支关系、五行计数和运限关系作为客观证据，把旺衰、格局、用神、调候保留为需要另选规则档案的解释层，避免模型把流派判断冒充排盘事实。

两个体系最终由 `web/ai-contract.js` 汇总为 `mingli-ai-input/v1`。契约会核对事实包校验状态、各动态层校验状态和请求范围；未列入 `supportedScopes` 的主题会抛出 `UNSUPPORTED_AI_SCOPE`，不会发送给模型。模型输入要求引用 JSON Pointer 事实路径，区分事实与解释，并禁止重算命盘、补造字段和作出医疗/投资/必然事件判断。

第一版解读层由 `web/ai-interpretation.js` 实现。其 `request(contract, { provider })` 接口是未来服务端网关的前端边界；当前只配置 `mock`，其他供应商会返回 `PROVIDER_NOT_CONFIGURED`。模拟输出和未来模型输出都必须通过 `mingli-ai-interpretation/v1` 验证，包括主题白名单、JSON Pointer 存在性、事实/解释标签、安全措辞和局限说明。只有验证通过的卡片才会进入 DOM。
