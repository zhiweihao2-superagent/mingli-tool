# 排盘字段与解释规则层边界

## 为什么身强弱、格局、喜用神、调候不等同于原始排盘字段

它们可以出现在用户熟悉的“排盘报告”里，但技术上不是同一层数据：

- 原始排盘字段由历法和固定表直接计算，例如四柱、藏干、十神、大运、流年、十二宫、星曜、四化。
- 规则派生结论需要在原始字段之上选择一套判定口径，例如如何计月令权重、怎样处理通根透干、何时按从格判断、格局优先级如何冲突消解、调候与扶抑用神谁优先。
- 不同门派的规则与优先级并不完全一致，所以这些结论必须携带规则档案、版本、逐步证据和冲突说明，不能伪装成唯一的历法事实。

## 上游八字 Skill 的实际规定

审计来源：`jinchenma94/bazi-skill`，固定提交 `112a5d84cd1a001a0038cafca3be68d93e4c0cc9`。

该 Skill 明确分成两段：

1. `scripts/pai_pan.py` 的标准输出负责输入、四柱、大运、流年、神煞；Skill 要求这些内容以脚本输出为准。
2. 后续“综合分析”要求模型另行判断得令、得地、得势，进而判断身旺、身弱、从强、从弱；根据月令和透干确定格局；参考《穷通宝典》摘要讨论调候和喜用神。

因此，上游并没有提供一个可复现、带版本的旺衰/格局/喜用神/调候确定性计算器，而是给模型一组分析指引与古籍摘要。项目现已用独立的 `bazi-derived-rules/v2` 实现候选规则层，并明确与历法排盘事实分离。v2 的可执行口径适配自 MIT 项目 `qilaidev/metaphysics-engine` 固定提交 `7631af8ddcd8bf2941fc00006c724c3b5de28fba`，包含：

- `ruleProfile`：采用的门派、权重和冲突优先级；
- `inputs`：引用到的四柱、月令、藏干、透干、合冲刑害等 JSON Pointer；
- `steps`：逐步判定及每步结果；
- `candidates`：身强弱、格局、用神和调候的候选结论；
- `counterEvidence`：不支持或破坏该候选的事实；
- `confidence` 与 `status`：候选、冲突或资料不足。

具体权重、候选排序和当前调候覆盖边界见 `docs/bazi-derived-rules.md`。

## 八字 7 主题报告结构

`mingli-report-plan/v2` 将 `bazi-derived-rules/v2` 的确定性结果拆成 7 个可独立校验的解释主题：四柱与日主、扶抑旺衰、格局与特殊格候选、喜用神三轴、调候寒暖燥湿、原局合冲刑害、大运与流年坐标。每个主题只携带本主题允许使用的八字 JSON Pointer；模型不能跨主题补算，也不能引用紫微证据替代八字结论。

## 紫微 13 主题报告结构

来源：`Renhuai123/ziwei-doushu` 的 `lib/ziwei/db-analysis.ts`，固定提交 `e478393ad6c865ad6270e978a3164d2f2cb5315b`。

本项目采用其公开的 13 个主题标签：命格总览、性格特质、感情婚姻、事业职业、财富运势、健康状况、兄弟合伙、子女缘分、迁移外出、人际贵人、田宅不动产、精神福德、父母长辈。

每个主题在 `mingli-report-plan/v2` 中具有：

- 对应本宫和对宫；
- 生年四化与宫干飞化的可解析 JSON Pointer；
- 一句话、核心解读、证据解释、经典出处和自我核对问题五个报告槽位；
- `evidence-ready` 或 `insufficient-evidence` 状态。

原仓库的 14 主星详细论断库明确未随开源代码发布，本项目不会复制不存在的内容。模型只能依据本项目实际排出的事实逐主题生成白话解释。

## 紫微格局候选

`web/vendor/renhuai-patterns.js` 是对上游公开 `lib/ziwei/patterns.ts` 的浏览器化适配。识别结果在报告计划中标记为 `matched-candidate`，并保留：

- 必须条件中已命中的项目；
- 加分项中已命中的项目；
- 已触发的破格项；
- 涉及宫位的事实路径；
- 古籍或上游规则所列来源。

格局候选不是现实事件结论。AI 只能在展示成立条件、反证和盘面路径后解释其传统含义，不能只报一个格局名称就下判断。
