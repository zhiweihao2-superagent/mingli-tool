# 已知限制

- 仅支持 1900 至 2100 年，且只支持北京时间。
- 真太阳时需要用户提供经度；当前没有内置城市经度检索。
- 中国历史夏令时会按上游历史日期表提醒，但不会静默扣除一小时；必须由用户确认出生证明记录采用夏令时后手动勾选。
- 时辰级“子”无法区分早子时与夜子时，因此明确按早子时处理。
- 上游测试通过只能证明固定样例与边界符合上游预期，不等于所有历法与命理规则都经过独立证明。
- 神煞和传统规则存在不同流派，当前输出只代表固定引擎的规则表。
- 尚未进行大规模第三方排盘案例对照。
- 当前是真实模型解读的本地测试阶段，尚未实现用户账户、数据库和小程序端。
- 不自动保存资料，也没有历史记录删除机制，因为当前根本不持久化。
- `references/classical-texts.md` 继承自上游，但当前程序不会自动将其送入模型生成解读。
- 晚子时（23:00–23:59）按次日建盘，不提供「视为当日」切换。依据：文墨天机 2.0.15 的默认配置就是「视为次日」（GlobalVars 初始化里 zzs 变量 = "2"，设置界面把 state 绑到 == "1"，即 1=当日、2=次日），iztro 的 `dayDivide="forward"` 同义。口径写在 `RULE_PROFILE.lateZishiRule`，每盘输出 `lateZishiPolicy` 供核对。注意：显示层的农历仍写输入当日的日期（iztro 的 `lunarDate` 不进位），起紫微用的「日」已进位，看到「农历廿一」而紫微按廿二算属于已声明的口径行为，不是随机错位。
- 博士十二神与文墨天机默认口径一致（`cycles.boshi12`，已逐宫对账 12/12，仅「官符/官府」写法不同）。岁前星、将前星照 iztro 通行口径产出在 `cycles.suiqian12`/`cycles.jiangqian12`，但文墨本命视图把岁建排到命宫、将星排到卯，起点不同则整排错位，属流派配置，**未对账**；这两排也没有并入 AI 合同（合同里没有对应 scope），所以 AI 解读既看不见也不会引用它们。
- 星曜亮度有四套（`knowledge/wmt/brightness.json`：斗数全书 qs／中州派 zz／现代修订一 xd1／现代修订二 xd2），默认 `qs`——依据文墨天机 2.0.15 出厂值 `GlobalVars.as:926 = "1"`（getter 里 "1"→`_AX_SB_QS`）与样盘 14 颗主星逐颗一致。切换用 `calculate(profile, { brightnessSchool })`，事实包输出 `brightness.{profile,label,wmtTable,alternates}`。只对 14 颗主星与文墨导出逐颗对过账（`docs/wmt-chart-crosscheck.md` 的 L2b）；辅星与小星的亮度来自同一张表，但没有逐一对照文墨，且该派不赋值的格子保持 `null`，不补猜。
- 小限与来因宫已结构化并做语义校验：小限按文墨常量表 `_AX_XIAOXIAN_ARR` 定起宫（申子辰见戌、巳酉丑见未、寅午戌见辰、亥卯未见丑）、男顺女逆，1–120 岁每岁恰落一宫（`small-limit-origin`，142 张盘全过）；来因宫取「宫干==生年干」那一宫，输出 `basics.originalPalace`（`original-palace` 全过），但按 SKILL §7 只作结构记录、不作判据。斗君尚未实现：文墨样盘写「子年斗君 卯」，其程序里只有文案没有算法，单点不足以定式，故不猜。

## §16 门禁与试读流程的口径（2026-11-04）

- **必需事实缺失 = blocked**，不再降级为 conditional。conditional 只表示「事实齐备、来源或一致性待核验」。
- **ready 需要三件事同时成立**：矩阵声明 ready、`factContractImplemented === true`、`section16Review.reviewer` 非空。三者缺一即 conditional。
- **关键事实按结构校验，不按非空校验**：`palaces` 必须 12 项且地支不重复；`sihua`/`daxianSihua`/`liunianSihua` 必须禄权科忌各一且不重复；`fourLayerDieGong.rows`/`dieGong.decadal` 必须 12 项；`flyingChains.palaceFlying` 必须与本盘十二宫×四化逐键一致。
- **矩阵结构不成立时整份无效**：`evaluateAll` 不产出逐行结果，调用方声明的 `expectedSteps` 不能把残缺矩阵放宽。
- **SKILL 锚点按规范化标题匹配**：去前导序号与尾注后相等才算命中；`§16` 这类章号允许前缀命中（后面必须是空白/分界符）；「紫微进阶」不会被「紫微」拉进来。同名标题在多颗星下重复属正常结构，按组装载并记 `ANCHOR_MULTI_SECTION`。
- **试读准备先跑事实门禁**：`scripts/trial_read_prepare.cjs` 产出 `gate.json`，并在每步提示词里写明门禁状态与缺口；第 6、15 项按试读规则强制 blocked，只允许输出未完成原因。
- **试读核验要求步骤覆盖恰为 1–15**：缺失、重复、越界都算覆盖不完整，`allCitationsValid` 为 false 并返回退出码 1（空目录不再被 `every()` 判成全部有效）。
- 仍未做：逐步事实合同（`factContracts`）的「检查项是否覆盖该步合同」这层语义仍未强制，调用方声明被忽略是当前的诚实做法；独立第三方审查仍无，`section16Review` 标注为 self-review。

## 入口页（第一屏）的口径

- 只显示**已经算过的盘**：命宫、身宫、五行局、命主身主、来因宫、大限区间、流年干支与虚岁、生年四化。
- 「今年三条主线」是**规则挑选**，不是解读：候选来自流年/大限四化的落宫（忌落命宫或身宫、忌落大限命宫、生年忌与流年忌同星、禄入命财官、权入命宫、科入命宫或官禄），按优先级排序取前三，每条带 `evidenceId` 可回盘面核对；没有命中就明说「相对平稳」，不硬凑三条。
- 逐月安排**在两块里**：只看「流月这一柱」与年/大运/流年之间的关系——出现 4 条以上冲刑害算「建议放慢」，合成 3 条以上且冲刑害不超过 2 条算「值得提前准备」，各取前三。
  整月全部关系（每月 20 条以上）不参与计数，否则没有区分度；不统计紫微流月，因为那属于年度视图的逐月细读。
- 本地记忆用 `localStorage` 键 `mingli.recent.v1`，最多留三条；没有 localStorage、坏 JSON、版本不符、写入失败都只降级并如实说明，不抛异常、不阻断排盘。
- 入口页是订阅者：排盘流程通过 `mingli:chart-ready` 事件通知它，它失败不影响排盘结果。

## 逐步骤事实合同（§16）

- 合同写在 `knowledge/ziwei/section16-fact-contracts.json`，每步声明它最少要哪些事实路径，**与本矩阵同源、逐条人写**。
- 门禁只判四件事：①合同是否声明（未装载合同簿 = 不升级 ready）②声明的路径是否都在矩阵 `requiredFacts` 里（不在就是「矩阵没为它背书」，判 blocked）③每条路径能否解析到非空值④能否过结构规则（四化必须禄权科忌各一、十二宫地支唯一等）。
- 合同的覆盖是**自洽性检查**，不是第三方证明：它保证「改了 requiredFacts 却没改合同」当场显形，但不能证明合同本身列全了判断所需的一切。这一层仍由签名的人负责。
- 审查独立性如实写 `self-review`：本项目没有独立第三方复核，门禁与文档都不冒充。要做独立复核，需要外部审查人签署 `section16Review.reviewerIndependence = independent` 并为每步补 `evidenceModel` 之外的判断依据。

## 前端版式与报告库（2026-11-04）

- 页面结构改为「页头导航 → 第一屏概览 → 排盘（表单 + 结果两栏）→ 解读 → AI 报告」，AI 报告不再埋在结果最底部，页头「AI 报告」可直接跳到该区块；若还没排盘，会提示先填出生资料。
- 视觉层只改 `web/styles.css` 的版式与 token（纸张底色、宋体标题、细线分隔、去掉阴影与渐变），不改任何判据、事实或解读文本。旧 token 仍被覆盖保留，回归测试不受影响。
- **报告库**（`web/report-archive.js`，本机 `localStorage` 键 `mingli.reports.v1`）：只存模型输出与已校验的引用（主题、白话、证据路径、引用 anchor），**不存出生资料**；同一体系同一主题序列会覆盖，最多保留 8 份，新的在前。
- 本地存储不可用、内容损坏、版本不符时一律降级：报告仍可在当前页面查看，只是不进报告库；写入失败不影响排盘与解读。
- 报告库是「本机浏览器」的能力，换设备或清浏览器数据就没了；服务端不保存、也没有账号体系。
- 页头徽标 `DeepSeek 测试` 只在服务端报告模型已配置时出现，不能作为「结果一定可信」的依据。
- **引用合并口径**：每批主题各自带 `knowledgeCitations`，整份报告的顶层数组是这些逐段引用的**并集**（去重、保持出现顺序），由客户端合并时统一回填，服务端在解码时也会补一次并显式写空数组。
- **没有专属摘录的主题**（年度主题就属于这种）：某一批资料与它无关时，省掉 `knowledgeCitations` 与写 `[]` 等价，校验按 `[]` 处理，不判「没标引用」；一旦该主题确实有可用锚点，仍然必须至少标一条，否则报 `TOPIC_CITATIONS_REQUIRED`。
- 年度报告（`annual-YYYY`）与八字、紫微报告一样进报告库，三者互不覆盖。

## 报告引用的两个口径（2026-11-05 修正）

- 整份报告的 `knowledgeCitations` 是逐段引用的并集，**即使并集为空也显式写成 `[]`**。字段缺失与「这批资料跟主题无关」在校验层是两件事，前者会被判成没标引用、整份作废。客户端合并多批结果、服务端解析模型输出时都按这条补齐。
- 某个主题本来就没有专属资料（年度六主题就是这种）时，段落省略 `knowledgeCitations` 等同于 `[]`；有专属资料的主题仍必须真的标一条，不能靠省略过关。
- 报告缓存键包含体系指纹，不只是出生信息。规则或事实层升级后指纹变化，旧缓存不再被复用。
- 多主题挤在一批里偶发「某段没标引用」，客户端会退化成单主题重发；仍然失败才向用户报错。

## 一页速览（2026-11-05）

- 排盘后先出现「先看这一页」：四柱、五行占比、喜用、命宫/身宫、12 宫方盘、选定年份的六条倾向。它只是把已有事实换一种排法，**不新增判据**。
- 六条倾向的规则：流年十神归族 + 紫微流年四化（忌/禄 落宫）+ 流年与年支/日支的冲合。措辞用「容易/多半」，出现「注定/必然/一定会」即视为缺陷（测试会拦）。
- 紫微流年四化只对「当前年份」计算；选其他年份时按八字流年给倾向，页面会写明这一点，不假装有紫微流年盘。
- 年份下拉只出现在标题右侧一处，正文里不再放第二个入口。
- 页面的 CSP 是 `style-src 'self'`：HTML 里写的 `style="…"` 会被浏览器丢弃，条形图这类按数值给宽度的元素会变成 0 宽。现在统一在渲染后通过 CSSOM 重新赋值（`applyDeferredStyles`），只处理 style 属性。
- 这里不提供「幸运色 / 幸运方位 / 幸运数字」这类结论：没有可核对的规则来源，写出来就是编。

## 解读为什么这样写（白话口径，2026-11-05）

- 触发原因：用户连问三次「解读晦涩」「看不懂我的运势」。问题不在事实层，而在提示词把模型当成了在写教材。
- 现在的硬约束（服务端 `_make_report_request` 里逐条写着，删掉就会退回旧腔调，`tests/test_ai_split_systems.py` 有回归钉住）：
  ① 全程用「你」，不写「命主」「此造」；
  ② `plainLanguage` 固定三段：这件事在你生活里对应什么 → 两三个具体场景 → 这段时间怎么做；
  ③ `oneLineSummary` 是人话标题，二十字以内，像朋友说话；
  ④ 术语每 150 字最多一个，第一次出现必须紧跟括号白话；
  ⑤ `plainLanguage` 里禁止出现证据/校验/候选/契约/路径/结构/数据，以及身强弱、七杀、藏干、月令、长生、格局、用神、宫位、四化等术语——它们只允许留在 `evidenceExplanation`（页面折叠区「为什么这样解读」）。
- 主题标题也换成人话（「你是什么底子」「你是偏硬还是偏软」「钱这件事」…），由合同下发、模型逐字使用，服务端不再让模型自己起名。
- 证据指针允许引用**许可路径的下级**：模型常把四柱引成 `/systems/bazi/chart/pillars/year/stem`，这在同一子树里，算本批之内；同级的其他事实仍会被拒。依据这一条，`EVIDENCE_OUTSIDE_TOPIC` 不再误杀正常引用。
- 仍未做：不做吉凶打分排名，不写幸运色/方位/数字；年度解读只到"这一年这件事"的粒度，不给具体日期与事件。

## 神煞条目（44 条）

- 已实现 44 条：原有 22 条 + plan-fill3 的 18 条 + 本轮补的 4 条（国印贵人、德秀、丧门、童子）。
- 国印贵人与德秀按「日干 / 月支三合」单一起算，不兼查年干，也不外挂第二版本。
- 童子只按「春秋寅子贵，冬夏卯未辰」的季节口诀查日支、时支，仅作提示性条目；
  民间另有按年柱纳音的分支说法，与季节口诀常冲突，故不并入判据、不参与打分。
- 未实现「披头」「勾绞」：公开表里同名规则的起算依据互相矛盾（披头有按年支、按日支、按三合沐浴位等多种）；

- 条目只说明「命中有这颗星」，不做吉凶判定；吉凶要看它在哪一柱、与哪些十神同宫。
